# Web access with a user-controlled switch

## Status

Implemented, 2026-10-13, on the local-only fork. Verified with unit tests and
against a web server on this machine; no internet fetch was made during
development.

## Problem

The local-only fork removed the `web_fetch` and `web_search` tools (commit
`102f435080`), so the model cannot look anything up. This brings web access
back as a mode under the user's control: a switch between a fully local mode
and a mode that allows web access, which only the user can flip.

## Goals

- Fully local stays the default.
- Only the user turns web access on or off, at any time, without a restart.
- The user approves every fetch, whatever the approval mode.
- A small tool: no page cache, no summarizing side model, no new
  dependencies.

## Out of scope

- Web search. The removed search tool used a cloud search API.
- Shell commands. The model can still reach the internet with commands such
  as `curl` when the user approves them; the shell stays unsandboxed by
  default, under the normal approval rules.

## Design

- **Setting.** `tools.webFetch`, a boolean, default `false`. It is in
  `WORKSPACE_RESTRICTED_SETTINGS`, so a project's settings cannot set it.
- **Switch.** `/web`, `/web on` and `/web off` save the setting in the user
  settings and call `Config.setWebFetchEnabled`. Built-in slash commands are
  never model-invocable. A hot-reload listener applies hand edits of
  `settings.json` the same way. The footer shows `web on` while it is on.
- **Registration.** `Config.syncWebFetchToolRegistration` registers the tool
  only when the setting is on and the session is not in bare or safe mode, and
  builds it at once, because `ToolRegistry.unregisterTool` does not remove
  pending factories. Switching calls `setTools()`, as `/advisor` does, so the
  model's tool list changes on the next request. With the setting off, the
  tool does not exist and the model does not see it.
- **Approval.** The invocation's `requiresUserInteraction()` returns `true`.
  The scheduler then asks in every approval mode, skips the auto-mode
  classifier, does not let hooks or allow rules approve, and hides "always
  allow". Headless runs cannot ask, so they never fetch; their warning no
  longer suggests `-y` when YOLO is already on. Deny rules (`WebFetch`) still
  apply. `execute()` also refuses when the setting is off, for a tool instance
  that outlives `/web off` (for example in a running subagent).
- **Fetch.** One GET with `redirect: 'manual'`, no cookies or credentials, and
  a fixed user agent without version or platform. Redirects are followed only
  to the same hostname, never from https to http, at most five times; any
  other redirect is returned to the model, so the next request needs a new
  approval. Limits: 30 s, 2 MB downloaded, 40,000 characters returned.
- **Content.** HTML is converted to text by a small converter in the tool:
  non-text elements are dropped, block elements become line breaks, links keep
  their absolute URL and `<pre>` keeps its whitespace. Text, JSON and XML are
  returned as they are; other types are not returned. The result is framed as
  untrusted page content.
- The loopback-only `fetchWithPolicy` used elsewhere is unchanged.

## Risks

- Prompt injection from fetched pages. Mitigated by per-fetch approval, which
  also stops a page from sending data out through the next URL, and by framing
  the content as untrusted.
- The regex converter is not an HTML parser. Unusual markup can produce messy
  text, and a page with many unclosed elements converts slowly; the 2 MB
  download limit bounds the cost.
- Turning the setting on changes the tool list, so the next request rereads the
  prompt instead of using the engine's cache.

## Validation

- Unit tests for the converter, the fetch (same-host and cross-host
  redirects, redirect limit, size limit, headers), the tool (validation,
  approval, results, refusal when off), `Config` registration and switching,
  `/web`, the hot-reload listener, the footer, the permission-rule alias and
  the headless warning.
- Interactive run of the bundle with Qwen3 4B, a throwaway home folder and a
  page served on `127.0.0.1`, inside a loopback-only sandbox. `/web` reported
  off; `/web on` saved the setting and showed `web on` in the footer; the
  model's call showed `WebFetch <url>` with only "Yes, allow once" and "No";
  after approval the server logged one GET with the fixed user agent and no
  cookie, and the model answered from the page; `/web off` saved `false` and
  removed the footer label.
- Headless run with the setting on and `--yolo`: the call was refused, the
  server logged no request, and the warning no longer suggests `-y` when YOLO
  is already on.

## Acceptance criteria

- With the setting off, no `web_fetch` tool is registered or offered.
- With it on, every fetch shows the URL and needs "Yes, allow once", in every
  approval mode.
- A project's `.qwen/settings.json` cannot turn it on.
